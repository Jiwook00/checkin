# 0007 - 측정한 코드가 운영 코드다: 관리자 화면과 리마인더 초안 생성 API

- 상태: 승인됨
- 날짜: 2026-10-30
- 관련 이슈: #79 (에픽 #72)
- 관련 커밋: 281d639, 6cc857e, 7912077, 7b2e6dc, cfccde4, 9651f66, 3687188
- 이전 결정: [0004 - 평가 하네스](0004-eval-harness.md), [0005 - 추출·근거·로컬](0005-extraction-evidence-local-models.md), [0006 - 생성·채점기](0006-generation-graders.md)

## 컨텍스트

#76까지 리마인더 생성을 평가 하네스(`scripts/eval/`)에서 쟀다. 그런데 실제 메일은 운영자 로컬의 Claude Code 스킬이 만들었다. 측정한 코드와 메일을 만드는 코드가 달랐고, 운영 기록(무엇을 넣어 무엇이 나왔고 사람이 어떻게 고쳤는지)도 남지 않았다.

이번 단계는 운영 경로를 **관리자 화면 + Edge Function + Claude API**로 옮긴다. 답할 질문은 넷이다.

1. 하네스와 운영이 같은 생성 코드를 쓰게 하려면 어디까지를 공유하고, 옮긴 뒤에도 같은 결과가 나온다는 것을 어떻게 보이는가
2. 관리자만 쓰는 기능을 멤버 전용 앱에 어떻게 넣는가 (권한을 어디서 판별하고, 멤버가 스스로 권한을 얻지 못하게 하려면)
3. 생성 호출을 어떤 단위로 나누고, 초안을 어떻게 저장해야 나중에 평가 데이터가 되는가
4. #76에서 평가한 생성 범위(콜백 + 공통 질문 + 공지)가 실제 운영에 충분한가

## 결정

### 순수 함수만 공유하고, 평가 개념은 하네스에 남긴다

`supabase/functions/_shared/reminder/`로 옮긴 것과 하네스에 남긴 것을 가르는 기준은 "운영에도 필요한가, 정답 라벨이나 개발용 도구에 기대는가"다.

| 옮김 (`_shared/reminder/`)                                        | 하네스에 남김 (`scripts/eval/`)                             |
| ----------------------------------------------------------------- | ----------------------------------------------------------- |
| 근거 검증(`evidence`), 추출·생성의 프롬프트·스키마·요청 빌드·파싱 | Stage 어댑터(`EvalCase` → 단계 입력)                        |
| 재료 선별(근거 통과분만), 메일 조립(`composeMail`)                | 합성 입력: 질문 스냅샷 매핑, 투표 상태, 공지                |
| 규칙 채점기(json · callback_match · form · voice · banned)        | `callback_label`(정답 라벨 `expectCallback` 필요)           |
| Claude API provider, 회고 본문 분류·대표글 선택, 해시             | LLM 채점(judge), claude-cli · ollama · echo, 호출 캐시·상한 |

- Stage를 통째로 옮기지 않은 이유: Stage의 `input()`은 `EvalCase`를 받는다. 운영 코드가 평가셋 개념(`expectCallback`, `notes`)에 묶이면 평가셋을 고칠 때마다 운영 코드가 흔들린다.
- LLM 채점은 개발용이다(ADR 0006). 매달 운영에는 사람이 검토하므로 judge가 없다. 규칙 채점기는 코드라 비용이 $0이고 결정적이어서 운영에도 붙였다. ADR 0006이 "P6에서 정한다"고 남긴 후속 과제의 답이다.
- 공지 구간(일정·투표 링크)과 `voteOpen`은 코어가 **입력으로 받는다**. 하네스는 지금처럼 case id 해시로 만든 합성값을, 운영은 다음 달 투표 회차의 실제 상태를 넣는다. LLM은 원래 `voteOpen` boolean만 보므로 프롬프트는 바뀌지 않는다.
- `_shared`는 URL import도 npm도 없는 순수 TS다. 하네스는 `parse-content`의 `deno.json`으로, Edge Function은 자기 `deno.json`으로 같은 파일을 import한다.

### 옮긴 뒤 같은 결과가 나온다는 것은 호출 캐시가 증명한다

하네스의 호출 캐시 키는 `sha256(provider · model · cacheTag · JSON.stringify(요청))`이다. 요청의 system·본문·스키마·max_tokens 중 한 글자, 키 순서 하나만 달라도 다른 키가 된다. 그래서 "옮긴 뒤 캐시가 100% 맞는다"는 것은 **모델에 보내는 요청이 바이트 단위로 같다**는 뜻이다. 점수를 다시 매겨 보는 것보다 강한 확인이고 비용이 들지 않는다.

- 이동은 손으로 하지 않았다. 원본 파일의 줄 범위를 스크립트로 잘라 붙여 프롬프트 문자열이 바뀔 여지를 없앴다.
- 요청 빌드 함수(`buildExtractRequest`, `buildGenerateRequest`)는 원래 인라인 객체의 키 순서(system → messages → maxTokens → jsonSchema)를 그대로 지킨다.
- `callback_label`을 하네스에서 덧붙일 때 채점기의 키 순서도 옮기기 전과 같게 맞췄다. 기록의 `scores`를 그대로 비교하려면 순서까지 같아야 했다.
- 비교 기준은 #76의 최종 run이 아니라 **옮기기 직전 코드로 새로 돌린 run**이다. #76 최종 run은 #78(공통 질문 DB 이관) 전이라, 생성 입력이 바뀐 case가 1건 있었다. 그 1건만 새로 호출해 기준선을 채운 뒤 옮겼다.

### 관리자는 컬럼 + SQL 함수로 판별하고, 트리거로 스스로 권한을 얻는 길을 막는다

`checkin_members.is_admin`과 `is_checkin_admin()`(SECURITY DEFINER, `search_path` 고정)을 두었다. RLS 정책, Edge Function, 앱 라우트 가드가 모두 같은 값을 본다.

- **컬럼만 추가하면 멤버가 자기 권한을 올릴 수 있었다.** `checkin_members`에는 본인 row UPDATE 정책이 있는데 `WITH CHECK`가 없고, 프로필 화면이 실제로 자기 row를 update한다. 그래서 `authenticated`·`anon` 롤이 `is_admin`을 켜거나 바꾸면 `BEFORE INSERT OR UPDATE` 트리거가 거부한다. 트리거 함수는 SECURITY INVOKER로 두어 `current_user`가 요청한 롤로 보이게 했다. 로그인 때의 upsert(`id, email, nickname`만 보냄)는 영향이 없다.
- 최초 관리자는 마이그레이션에 넣지 않고 적용 후 SQL로 한 번 지정했다. 리포가 공개라 운영자의 신원을 커밋하지 않는다.
- Edge Function은 `verify_jwt = false`(기존 함수와 같음)로 두고 함수 안에서 JWT로 유저를 확인한 뒤, 사용자 권한으로 `is_checkin_admin()`을 RPC로 묻는다. 관리자 판별 로직을 함수마다 다시 쓰지 않는다.

### 생성은 멤버별로 부르고, 초안은 덮어쓰지 않고 쌓는다

`generate-reminders`는 `{ session, memberId }` 하나를 받는다. 화면이 대상 멤버를 동시 2명씩 부른다.

- 멤버별로 나눈 이유: 호출 하나가 2~10초라 함수 한도(150초)와 멀다. 한 명이 실패해도 나머지는 남고, 실패는 그 멤버 카드에만 보인다. "이 멤버만 다시 생성"이 같은 경로다.
- `checkin_reminder_drafts`에는 `(session, member_id)` unique를 두지 않고 생성할 때마다 row를 쌓는다. 화면은 멤버별 최신 row를 보여 준다. 반려된 초안도 지우지 않는다. 그것이 #84·#77의 사람 라벨이다.
- row마다 입력 스냅샷(재료·근거 탈락 수·공통 질문·공지·직전 회고 id와 해시·본문 상태), 추출·생성 출력, 모델, 프롬프트 해시, 토큰, 지연, 규칙 채점을 남긴다. 프롬프트 해시는 하네스 run config와 같은 방식이라, 운영 초안이 어느 평가 run의 프롬프트로 만들어졌는지 맞춰 볼 수 있다.
- 추출 결과는 같은 본문 해시와 같은 추출 프롬프트 해시를 가진 이전 row가 있으면 재사용한다. 별도 캐시 테이블은 두지 않았다.
- INSERT 정책이 없어서 초안은 service role(Edge Function)만 만든다. 관리자는 읽기와 **검토 컬럼(status, edited_mail, review_note, reviewed_at) UPDATE만** 할 수 있게 컬럼 단위로 권한을 좁혔다. 생성된 `mail`·`output`을 바꿀 수 있으면 라벨의 기준(모델이 무엇을 냈는가)이 흔들린다. 수정본은 `edited_mail`에 따로 둔다.

### v1은 #76에서 평가한 범위 그대로이고, 이미 쓴 멤버는 만들지 않는다

생성 범위는 인사 · 콜백 · 공통 질문 · 공지 · 맺음이다. 반응(이모지·댓글) 블록과 결석 분기별 본문은 #85로 미뤘다.

- 이번 회차에 이미 글을 쓴 멤버는 생성하지 않고 "이미 씀"으로만 표시한다. v1 프롬프트는 "회고를 이제 쓸 수 있어요"로 여는 메일이다. 스킬 체크리스트의 "이미 쓴 사람에게 '쓰세요' 문구 금지"에 걸리고, 이 분기의 내용(감사·받은 반응)은 #85 범위다.
- 직전 회차 글이 없으면(오래 쉼·신규) 콜백 없이 생성한다. 쉰 기간을 세는 표현은 프롬프트와 `banned`가 막는다.
- 직전 회차 대표글은 평가셋과 같은 규칙으로 고른다(본문 정상 > 모호 > 실패, 긴 글, 먼저 쓴 글). 반응 수처럼 시점에 따라 바뀌는 기준은 쓰지 않는다. 평가셋이 제외했던 '모호' 본문(degraded, 짧은 직접 작성)도 생성에 쓴다. 지어낸 인용은 근거 검증이 거른다.
- 공통 질문이 승인되지 않은 회차는 생성을 막는다(400). 메일과 앱 배너가 같은 질문을 써야 하기 때문이다.

### 공통 질문 제안은 작게 두고 평가하지 않는다

`suggest-questions`는 이미 쓴 질문과 후보 뱅크를 보고 Haiku가 후보 3개와 이유를 낸다. 고르는 것은 사람이고 기록도 남기지 않는다. 가치가 낮은 기능이라 평가 비용을 쓰지 않기로 했다. 이미 쓴 질문과 같은 후보는 모델이 어겨도 코드가 거른다. 뱅크는 프론트 한 곳에 정의하고 요청에 실어 보낸다.

## 검토한 대안

### 대안 A: 회차 한 번 호출로 8명을 함수 하나에서 병렬 처리

- **장점**: 호출이 한 번이라 화면 코드가 단순하다.
- **단점**: 부분 실패와 재시도를 함수 안에서 다시 설계해야 한다. 한 명 다시 생성은 결국 별도 경로가 필요하다.

### 대안 B: Stage를 통째로 `_shared`로 옮긴다

- **장점**: 하네스와 운영이 완전히 같은 객체를 쓴다.
- **단점**: 운영이 `EvalCase` 모양을 꾸며 넣어야 한다. 평가셋 필드가 바뀌면 운영 코드가 같이 바뀐다.

### 대안 C: 관리자를 별도 테이블(`checkin_admins`)로 둔다

- **장점**: 쓰기 정책이 없는 테이블이라 구조적으로 안전하다. 기존 멤버 정책을 건드리지 않는다.
- **단점**: 이슈 설계(컬럼 하나)에서 벗어나고 조회가 하나 늘어난다. 트리거로 같은 안전성을 얻을 수 있어서 컬럼을 택했다.

### 대안 D: 컬럼 GRANT를 다시 정의해 `is_admin` UPDATE 권한만 뺀다

- **단점**: 로그인 upsert와 프로필 수정 경로가 쓰는 컬럼을 모두 다시 나열해야 한다. 나중에 컬럼이 추가될 때마다 빠뜨리기 쉽다. drafts에는 반대로 "허용할 컬럼"이 4개로 고정이라 이 방식을 썼다.

### 대안 E: drafts를 `(session, member_id)` unique로 두고 다시 생성하면 덮어쓴다

- **단점**: 반려된 초안과 그 사유가 사라진다. 그 기록이 사람 라벨이 되는 것이 이 재설계의 목적이었다.

### 대안 F: 운영에도 LLM 채점을 붙인다

- **단점**: 매달 비용이 생성의 수십 배가 된다(ADR 0006: 채점 API 환산이 생성의 약 25배). 사람이 어차피 한 통씩 읽는다. LLM 채점이 사람과 얼마나 맞는지는 #77에서 보고 정한다.

### RLS 확인 (멤버·관리자·익명 롤, 트랜잭션 롤백으로 데이터 남기지 않음)

- 멤버: 자기 `is_admin` 올리기 거부(트리거), 프로필 update와 로그인 upsert는 정상. 질문 쓰기 거부, proposed 질문 안 보임. drafts 0건 조회, 쓰기 거부
- 관리자: proposed 질문 조회와 질문 등록·승인 허용. drafts 조회와 검토 컬럼 수정 허용. `mail` 직접 수정과 INSERT는 거부. 자기 `is_admin` 내리기도 거부
- 익명: drafts와 `is_checkin_admin()` 모두 거부
- 배포된 함수: 토큰 없으면 401, 로그인이 아닌 키로도 401

| 사람 검토      | 반려 1건(사유 기록). 규칙 채점이 걸린 그 메일이다     |

- **규칙 채점기는 사람 검토 전 점검으로 쓸 만했다.** 사람이 반려한 유일한 메일을 규칙 채점기도 걸렀다. 한 건이라 일반화할 수는 없지만, 운영에 붙인 판단을 뒷받침한다.
- **반려 사유는 평가에서 보지 못한 실패 유형이었다.** 모델이 직전 회차 **공통 질문에 대한 답**을 콜백 재료로 골랐다. 사람은 "지난달 모두에게 던진 주제를 다시 꺼내는 것은 어색하다, 그 사람의 일정이나 근황 대목이 더 자연스럽다"고 적었다. 추출 단계는 그 회차의 공통 질문을 모르고, 회고 본문에 섞인 질문 답변을 다른 대목과 구별 없이 뽑는다.
- **v1 범위는 "메일이 나간다"는 점에서는 충분했고, "개인 메일"로서는 약했다.** 8명 중 5명이 콜백 없는 메일을 받는다. 직전 회차 글이 없는 멤버가 운영에서는 다수였다. 평가셋은 콜백 사례 위주로 만들어 이 비율이 드러나지 않았다. 결석 분기와 반응 블록(#85)이 필요하다는 근거다.

## 알려진 한계

- **공통 질문 답변을 콜백 재료로 고른다.** 평가셋도 같은 구조(본문에 공통 질문 답변이 섞임)지만, 하네스의 공통 질문은 합성 입력이었고 judge 기준에도 이 항목이 없어 잡히지 않았다(ADR 0006 한계). 고치려면 추출 프롬프트나 재료 선별이 바뀌고, v3 기준선과 호출 캐시가 끊긴다. 그래서 이번에는 고치지 않고 사람 검토에 맡겼다.
- **콜백 없는 메일이 다수다.** v1은 오래 쉰 멤버와 신규 멤버를 따로 쓰지 않는다. 콜백 없는 메일은 LLM 채점 대상도 아니다(ADR 0006).
- **'모호' 본문 경로는 평가되지 않았다.** 평가셋이 제외한 영역이고, 첫 운영에서도 이 경로를 탄 멤버는 없었다.
- **이미 쓴 멤버에게는 메일이 없다.** 원래 스킬은 감사와 받은 반응을 전했다.
- **공지는 코드가 정한 문구다.** 확정된 모임의 링크(meeting_url)는 넣지 않는다. 투표가 닫혔지만 확정 전이면 일정 줄을 비운다(날짜를 지어내지 않는다). 필요하면 검토에서 사람이 고친다.
- **복사는 평문이다.** 원래 스킬의 HTML 템플릿은 옮기지 않았다.
- **관리자 경로의 end-to-end는 사람이 화면으로 확인했다.** 관리자·비관리자 JWT로 함수를 부르는 자동 확인은 없다(테스트 프레임워크 없음).
- **최악의 경우 함수 한도를 넘을 수 있다.** 추출과 생성이 모두 60초 타임아웃 + 재시도 1회까지 가면 이론상 150초를 넘는다. 실제 최대는 10.3초였다.
- `is_admin`은 멤버 목록을 읽을 수 있는 모든 멤버에게 보인다. 누가 관리자인지는 비밀이 아니라고 보았다.

## 후속 과제

- **#84 실제 한 회차 운영**: 승인·수정·반려를 끝까지 하고 발송한다. 검토 기록을 `local/eval/dataset/`의 사람 라벨로 내보내고, 통수·비율·토큰·지연을 drafts에서 집계한다. 이번에 나온 "공통 질문 답변 재료"가 몇 통에서 반복되는지 센다.
- **공통 질문 답변 재료 대응**: 후보는 둘이다. (a) 추출 입력에 그 회차의 공통 질문을 넘겨 답변 대목을 제외시킨다. (b) 코드로 질문 문장과 겹치는 대목을 걸러낸다. ADR 0006의 원칙(사실은 코드가 맡는다)대로라면 (b)가 먼저다. 어느 쪽이든 기준선을 다시 잰다.
- **#85 범위 확장**: 결석 분기별 본문, 반응 블록, 이미 쓴 멤버용 메일, HTML 템플릿, 메일 API 발송. 첫 운영에서 콜백 없는 메일이 5/8이었다는 것이 우선순위의 근거다.
- **#77 사람 평가 일치도**: 라벨 출처는 운영 검토 기록이다. 반려 사유처럼 judge 기준에 없는 실패 유형이 나오면 기준에 넣을지를 함께 정한다.
