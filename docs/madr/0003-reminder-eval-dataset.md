# 0003 - 리마인더 평가셋을 기존 회고 데이터에서 만든다

- 상태: 승인됨
- 날짜: 2026-10-23
- 관련 이슈: #73 (에픽 #72)
- 관련 커밋: dcc7c90, 5a921b7, 310e0cf

## 컨텍스트

갈피 리마인더는 멤버마다 지난달 회고의 한 대목을 짚는 개인 콜백을 넣어 보낸다. 지금은 사람이 Claude Code 스킬로 생성하고 검토한 뒤 수동으로 발송한다. 이 생성을 "추출 → 생성 → 검토" 파이프라인으로 바꾸려는데, 프롬프트나 모델을 바꿨을 때 좋아졌는지 나빠졌는지 판단할 기준이 없다.

평가 하네스(#74~)에 먹일 고정 입력이 필요하다. 조건은 세 가지다.

1. 사람이 정답을 새로 달지 않아도 되어야 한다. 1인 프로젝트라 라벨링에 쓸 시간이 없다.
2. "콜백을 잘 만드는가"뿐 아니라 "근거가 없을 때 콜백을 만들지 않는가"도 잴 수 있어야 한다.
3. 같은 DB 상태에서는 항상 같은 case 목록이 나와야 한다. 실행 사이의 점수 차이가 프롬프트 때문인지 데이터 때문인지 가려야 한다.

데이터 사정도 있다. 과거 회고 상당수가 노션·티스토리 링크였는데 비공개로 바뀌어 파싱에 실패했고, 그런 글은 본문이 비어 있다(`parse_status = 'failed'`).

## 결정

**이미 있는 회고 이력에서 case를 뽑고, 본문이 없는 글은 버리지 않고 "콜백이 없어야 정답"인 음성 사례로 쓴다.** 평가셋은 `scripts/eval-dataset.ts`가 만들고, 스냅샷은 `local/eval/dataset/`(git 제외)에만 둔다.

### 평가 단위

멤버 m이 회차 N+1에 글을 썼다면, "N+1 글을 쓰기 전에 받았을 리마인더"가 case 하나다. N은 존재하는 회차를 정렬한 순서상 직전 회차다(빠진 달은 건너뛴다).

| 유형                             | 조건                   | 기대 정답                  |
| -------------------------------- | ---------------------- | -------------------------- |
| `callback`                       | m의 N 글이 본문 정상   | 콜백이 들어간다            |
| `no_source` (`parse_failed`)     | m의 N 글이 `failed`    | 콜백이 없다                |
| `no_source` (`not_participated`) | m이 N에 글을 쓰지 않음 | 콜백이 없다                |
| `reference`                      | 실제로 발송한 7월 메일 | 참고 답안 (정답 고정 아님) |

기대 정답은 `expectCallback` 필드로 데이터에 직접 적는다. 채점기가 유형을 해석하지 않고 이 값만 보게 하려는 것이다.

### 메일의 큰 틀

메일은 다섯 구간으로 나눠 저장한다: `opening`(인사) · `callback`(지난 회고 짚기) · `commonQuestion`(공통 질문) · `notice`(공지·안내) · `closing`(마무리). 지난달 글이 없으면 `callback` 구간이 통째로 빠진다. 형식과 말투는 앞으로 바뀔 예정이라 reference는 "그대로 맞출 정답"이 아니라 참고 답안으로만 쓴다.

### 중복 제거

- **같은 멤버·같은 회차의 여러 글** → 하나만 남긴다. 본문 정상 > 본문 길이 > 먼저 등록 > id 순이다. 반응 수처럼 시간이 지나면 바뀌는 기준은 쓰지 않는다(재현성).
- **같은 멤버의 다른 회차에 본문이 완전히 같은 글** → 가장 이른 회차만 남긴다. 이때 지워진 회차가 직전·현재 회차인 case는 참여 여부를 단정할 수 없어 만들지 않고 제외 사유를 남긴다.
- **판정이 애매한 글**(`degraded`, 200자 이하 직접 작성)은 직전 글일 때 case를 만들지 않고 제외한다. 이번 데이터에는 0건이었다.

### 개발용 서브셋 20건

유형과 본문 길이로 층화한다: `callback` 9건(본문 길이 3구간 × 3), `no_source` 7건(`parse_failed` 4 + `not_participated` 3), `reference` 4건 전부. 길이 구간 경계(3600 / 5050자)는 전체 분포의 3분위수를 보고 한 번 정해 상수로 고정했다. 데이터가 늘어도 구간이 움직이지 않게 하려는 것이다. seed는 73이고, 층마다 PRNG를 따로 둬서 한 층의 후보가 바뀌어도 다른 층의 결과가 흔들리지 않는다. 한 멤버가 한 그룹에서 3건 이상 뽑히지 않게 상한을 둔다.

### 재현성

`manifest.json`에 case id 목록의 sha256을 남기고, `--check`가 DB에서 다시 계산해 비교한다. id가 달라지면 추가·삭제된 id를 보여주고 exit 1로 끝난다. 일부러 manifest를 틀어서 이 검사가 실제로 잡아내는지 확인했다.

## 검토한 대안

### 대안 A: 정답을 손으로 새로 만든다

사람이 회고마다 "좋은 콜백"을 직접 쓴다.

- **장점**: 정답의 품질을 통제할 수 있다.
- **단점**: 시간이 많이 들고, 정답을 쓰는 기준이 그대로 채점 기준이 되어 평가 대상과 구분이 흐려진다. 이미 있는 데이터로 시작해서 필요할 때 사람 라벨(약 30건, #78)을 따로 얹는 편이 낫다.

### 대안 B: LLM으로 합성 평가셋을 만든다

LLM이 가상의 회고와 정답 콜백을 만든다.

- **단점**: 평가받는 모델과 평가셋을 만드는 모델이 같은 계열이면 편향이 생긴다. 실제 멤버의 글이 가진 길이·문체·이미지 마크다운 같은 거친 면이 빠진다.

### 대안 C: 본문이 있는 글만 쓴다

`failed` 글을 평가셋에서 뺀다.

- **단점**: 지어낸 콜백이 가장 나쁜 실패인데, 근거가 없을 때 콜백을 만들지 않는지는 이 사례로만 잴 수 있다. 추출 단계가 빈 입력에서 얼마나 조용히 틀리는지도 같이 드러난다.

### 대안 D: 본문 앞 80자로 중복을 판정한다

처음 이슈에 적힌 기준이다.

- **단점**: 같은 양식(KPT 템플릿 머리말, 이미지 줄로 시작하는 노션 글)을 쓰는 서로 다른 글이 중복으로 잡힌다. 실제로 확인한 결과 본문 전체가 같은 쌍은 한 쌍뿐이었다. 정규화한 본문 전체 일치로 바꿨다.

`callback` 본문 길이는 min 400 · p50 4288 · max 12074자다. 멤버 8명 중 한 명은 case가 1건뿐이고, 두 명은 `no_source`가 절반을 넘는다(19/33, 20/26). 멤버별 편중은 `summary.md`에서 볼 수 있다.

**기준선(이슈 #72)과의 차이**

- 이슈와 같은 정의(중복 제거 전)로 세면 콜백 사례가 정확히 142건이다. 중복 제거로 같은 멤버의 2건이 빠져 140건이 된 것이다.
- 원본 행은 219건(기준선 217), 본문 정상은 172건(168), `failed`는 47건(48)이다. 직접 작성한 글 4건은 `parse_status`가 null인데, 기준선이 이 4건을 집계에 넣었는지는 확인하지 못했다. 나머지 차이(행 +2, `failed` -1)의 원인도 확인하지 못했다. 기준선을 조회한 뒤 글이 추가·수정됐을 가능성이 있지만 추측이다.

**알려진 한계**

- `reference`는 4건이고, 그중 1건은 규칙과 어긋난다. 7월 메일이 직전 회차 글이 아니라 그 앞에 쓴 글을 인용했다(`ruleDeviation`으로 표시). 말투 참고용으로는 남기되 정답 기준은 "콜백 없음"으로 둔다.
- 평가셋 전체를 프롬프트 튜닝에도 쓰면 같은 데이터에 맞추게 된다. 개발은 서브셋 20건으로 하고 전체는 비교 실행에만 쓰는 식으로 나누되, 별도의 홀드아웃 분할은 아직 없다.
- 규칙 채점기의 "본문 4~7문장"은 기존 스킬 기준이다. 메일 구조가 다섯 구간으로 바뀌었으므로 구간별 규칙으로 다시 정해야 할 수 있다(#76).
- 회고 원문은 `local/eval/`에만 있다. 저장소에는 스크립트와 이 문서만 올라가므로, 다른 환경에서 재현하려면 DB 접근 권한이 필요하다.
