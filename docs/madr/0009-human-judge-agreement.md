# 0009 - judge는 좋은 메일을 깎지 않는지까지만 믿는다: 사람 라벨과 LLM 채점 일치도

- 상태: 승인됨
- 날짜: 2026-11-02
- 관련 이슈: #77 (에픽 #72)
- 관련 커밋: fb6ce97, 95f2b46, 746d346, 6480e37, 567fba0
- 이전 결정: [0006 - 생성·채점기](0006-generation-graders.md), [0008 - 운영 검토 기록을 사람 라벨로](0008-review-records-as-human-labels.md)

## 컨텍스트

ADR 0006의 LLM 채점기(judge: Sonnet 5.5, `claude -p`, grounded·specific·tone 0/1/2)는 프롬프트를 고칠 때 개선 여부를 가르는 기준이었다. 그런데 judge끼리의 일치(Sonnet–Opus 87%)만 확인했고, 같은 Claude 계열이 생성과 채점을 하므로 자기 선호 편향이 있을 수 있었다. 기준은 메일을 실제로 보내는 사람(운영자)의 판단이다.

답할 질문은 셋이다.

1. judge는 운영자와 얼마나 같은 판단을 하는가
2. 어긋나는 곳은 채점 기준으로 고칠 수 있는가
3. 결국 어떤 항목은 자동 채점을 믿고, 어떤 항목은 사람이 봐야 하는가

## 결정

### 라벨 30건: 운영 3 + 하네스 27, judge 점수 층별로 고른다

| 출처                         | 건수 | 집합 | 용도                                   |
| ---------------------------- | ---: | ---- | -------------------------------------- |
| 운영 2026-10 최종 row (콜백) |    3 | 보정 | ADR 0008 운영 라벨과 같은 메일         |
| tune 콜백                    |   15 | 보정 | judge 점수 low 1 · mid 4 · high 10     |
| tune `no_source`             |    2 | 보정 | 콜백 없는 메일(judge 대상 아님) 확인용 |
| holdout 콜백                 |    9 | 확인 | low 1 · mid 4 · high 4                 |
| holdout `no_source`          |    1 | 확인 |                                        |

- 층은 기준 run(v3 최종, ADR 0006)의 judge 점수로 나눴다. high만 고르면 일치율이 부푼다. low는 tune·holdout에 1건씩뿐이라 모두 넣었다. 시드 고정.
- **보정과 확인을 나눈다.** judge 기준은 보정 집합(운영 + tune)의 어긋난 case만 읽고 고친다. 확인 집합(holdout)은 보정 전후 숫자만 본다. ADR 0006의 tune/holdout 원칙을 judge 보정에도 적용했다.
- judge 비교 대상은 콜백 메일 27건이다(judge는 콜백 없는 메일을 채점하지 않는다).

### 사람은 블라인드로, judge와 같은 3항목 0/1/2 + 메모

정적 HTML 시트 한 장에 직전 회고 원문·추출 재료·생성 메일을 나란히 놓고, 항목별 점수와 한 줄 메모를 받았다. judge 점수·층·집합은 시트에 넣지 않았고 순서를 섞었다. 운영 3건도 ADR 0008의 태그에서 옮기지 않고 같은 형식으로 다시 라벨했다.

### 라벨을 judge 정의에 맞춰 나눈다 (원점수는 보존)

라벨을 받은 뒤 두 가지가 judge 정의와 다른 뜻이었다. 운영자에게 확인하고 나눠 셌다.

- **스펙 결함**: tone 1점 23/30건은 모두 생성 프롬프트가 지시한 여는 안내 문장 때문이었다(ADR 0008의 `tone_other` 7/7과 같은 원인). judge는 스펙에 맞는지를 보므로 이것을 잡을 수 없다. 비교용 tone은 이 문장을 뺀 점수(2)로 두고, 원점수는 따로 보고한다.
- **재료 선택**: grounded 1점 11/27건은 사실 오류가 아니라 "더 알맞은 재료가 있었다", "이미 끝난 일이다", "질문을 이렇게 물었으면" 같은 재료 선택·질문 방식 문제였다. judge의 grounded는 "고른 재료에 있는 사실만 말하는가"다. 비교용 grounded는 2로 두고 재료 선택 문제를 따로 센다.

### judge 보정은 tone만 남긴다

| 보정                                                                                    | 근거 (보정 집합)               | 결과       |
| --------------------------------------------------------------------------------------- | ------------------------------ | ---------- |
| tone: opening의 회고 안내 문장, closing의 가벼운 끝인사는 정해진 형식이라 감점하지 않음 | judge tone 1 / 사람 2: 2건     | 유지       |
| tone: 진행 중인 일이 어떻게 되어 가는지 묻는 것은 근황 질문이지 검사가 아님             | 사람 메모 5건이 이 질문을 선호 | 유지       |
| specific: 열린 질문이라도 그 대목에서 이어지면 2                                        | judge specific 1 / 사람 2: 5건 | **되돌림** |

specific 보정은 라벨 27건에서 일치도를 올렸지만(보정 집합 61% → 83%), 전체 211건을 다시 채점하자 **specific이 140건 모두 2점**(0.940 → 1.000)이 됐다. 변별력이 사라진 것이다. 라벨 일치도가 오른 것은 사람 점수가 대부분 2점이라 "모두 2점을 주는 judge"도 맞아 보였기 때문이다. 그래서 되돌렸다.

**사람 점수가 한쪽에 몰린 작은 라벨셋에서는 일치도만으로 보정을 판단하지 않는다. 전체 run의 점수 분포(2점 미만 건수)를 함께 본다.**

### "이행 확인"을 재는 채점은 만들지 않는다

ADR 0006은 "judge tone이 정중한 이행 확인을 잡지 못한다"를 한계로, 이를 재는 채점을 후속 과제로 남겼다. 운영자 기준은 반대였다. "했나요"처럼 지켰는지 따지는 질문은 피하되, "어떻게 되어 가고 있나요"처럼 진행 상황을 묻는 질문은 오히려 낫다고 봤다(문맥에 따라 "했나요"가 맞는 경우도 있다). 그래서 이행 확인 채점 대신 tone 기준에 "진행 질문은 검사가 아니다"를 적었다. 생성 쪽 반영은 #85로 넘긴다.

## 검토한 대안

- **LLM으로 라벨을 붙인다**: judge끼리의 비교가 되어 자기 선호 편향을 볼 수 없다(ADR 0006에서 이미 했다).
- **운영 라벨을 태그에서 옮긴다**: 태그는 항목 점수가 아니라 judge와 바로 비교할 수 없고, 하네스 라벨과 형식이 달라진다.
- **사람에게 judge 점수를 보여 준다**: 판단이 judge에 끌린다.
- **보정·확인 집합을 나누지 않는다**: 보정이 라벨 30건에만 맞았는지 알 수 없다.
- **재료 선택을 judge 넷째 항목으로 넣는다**: 사람이 가장 많이 지적한 곳이지만, 스키마가 바뀌어 이전 run과 비교가 모두 끊긴다. 근거도 보정 집합 6건뿐이다. 생성 쪽(#85)에서 다룬다.
- **specific을 중간 문장으로 다시 고친다**: 보정 집합 18건으로 한 번 더 맞추면 과적합 위험이 크다.

## 결과

2026-11-02. judge Sonnet 5.5, Claude Code 2.1.316(실험 중 고정), 생성은 v3 기준 run의 캐시(바이트 단위로 같은 요청인지 호출 캐시로 확인: 하네스 24/24). 회차마다 같은 글을 2번 채점했다(a / b). 청구 없음(구독).

### 일치도 (정확 일치, a / b)

| 항목                    | 보정 집합 n=18: 보정 전 → 최종 | 확인 집합 n=9: 보정 전 → 최종 |
| ----------------------- | ------------------------------ | ----------------------------- |
| grounded                | 83 / 83% → 83 / 83%            | 78 / 89% → 89 / 89%           |
| specific                | 61 / 56% → 67 / 56%            | 78 / 56% → 56 / 44%           |
| tone (스펙 결함 제외)   | 89 / 94% → 100 / 100%          | 100 / 89% → 100 / 100%        |
| tone 원점수             | 17 / 22% → 28 / 28%            | 11 / 22% → 11 / 11%           |
| grounded 원점수         | 56 / 67% → 61 / 56%            | 22 / 33% → 33 / 33%           |
| 회차 간 바뀐 judge 항목 | 6/54 → 7/54                    | 4/27 → 4/27                   |

- 보정 전후 차이는 대부분 흔들림 폭(회차 간 바뀐 항목 약 11~15%, 18건 기준 항목당 ±2건) 안이다. tone의 상승도 1~2건이다.
- judge가 사람보다 낮게 준 항목: grounded 3/18, specific 3~6/18. 높게 준 항목: specific 2~3/18. 사람보다 높게 준 specific 중 다수는 공통 질문 문장을 재료로 쓴 메일이다. judge는 직전 회차 공통 질문을 입력으로 받지 않아 구조적으로 못 본다.
- 원점수 기준으로 비교했다면 tone 11~28%, grounded 22~67%로 "judge를 못 믿는다"는 결론이 났을 것이다. 사람과 judge가 같은 이름으로 다른 것을 쟀다.

### 전체 run (새 기준선 = g11)

| run                    | judge 프롬프트 | grounded        | specific      | tone      |
| ---------------------- | -------------- | --------------- | ------------- | --------- |
| v3 최종 (CLI 2.1.311)  | 657095b4       | 0.946 (13건 <2) | 0.946 (15)    | 0.979 (6) |
| tone + specific 보정   | 6ae4e65d       | 0.954 (10)      | **1.000 (0)** | 0.979 (6) |
| **tone 보정만 (채택)** | e7a37f4c       | 0.936 (13)      | 0.904 (27)    | 0.986 (4) |

콜백 140건 기준, 괄호는 2점 미만 건수. 채택한 judge의 specific은 v3 최종보다 엄격하다(2점 미만 15 → 27). 그사이 CLI 버전과 tone 문장이 함께 바뀌어 원인을 하나로 가를 수 없다. 이후 비교는 이 run을 기준으로 한다.

### 사람 라벨이 보여 준 것 (judge 밖)

| 항목                              | 건수 (분모)                      |
| --------------------------------- | -------------------------------- |
| 스펙 결함 (여는 안내 문장)        | 23 (전체 30)                     |
| 재료 선택·질문 방식 문제          | 11 (콜백 메일 27)                |
| 그중 공통 질문 문장·답이 재료     | 2 (보정 집합 콜백 18, 태그 기준) |
| 사실 오류 (grounded 0~1, 나눈 뒤) | 0 (콜백 메일 27)                 |

### 자동 채점을 믿을 수 있는 범위

**사실(grounded)과 톤(tone)은 judge가 운영자와 83~100% 일치해, 프롬프트를 고칠 때 회귀 점검으로 믿어도 된다. 다만 사람 라벨이 모두 2점이었으므로 확인한 것은 "좋은 메일을 깎지 않는가"까지이고, 나쁜 메일을 잡는 능력은 검증하지 못했다. 구체성(specific)은 judge가 사람보다 엄격하고 일치도(44~67%)가 흔들림 폭 안에서 움직이므로, 평균의 방향만 참고하고 개별 판정은 사람이 본다. 재료 선택·질문 방식(콜백 메일의 41%), 공통 질문 재료, 프롬프트가 만든 스펙 결함은 judge 밖이라 사람이 본다. 운영자가 실제로 가장 많이 고친 곳이 바로 여기였다.**

## 알려진 한계

- **라벨러가 한 명이다.** "운영자 기준과의 일치도"이고, 메일을 받는 멤버의 느낌과는 다를 수 있다.
- **표본이 작다.** 콜백 메일 27건, 확인 집합 9건이다. 회차 간 흔들림이 개선폭과 비슷하다.
- **사람 점수가 한쪽에 몰렸다.** 나눈 뒤 grounded·tone은 전부 2점, specific은 2점 미만이 5건뿐이라 judge의 "잡아내는 능력"은 재지 못했다. 나쁜 메일을 일부러 섞은 라벨이 있어야 잴 수 있다.
- **라벨 정의를 사후에 나눴다.** 스펙 결함과 재료 선택은 라벨을 받은 뒤 운영자 설명으로 나눴다. 시트의 점수 기준 설명이 충분하지 않았다.
- **태그는 보정 집합만, 운영자의 메모를 보고 대신 붙였다.**
- **CLI 버전**: 실험 내내 2.1.316으로 고정했지만, v3 최종 run(2.1.311)과의 차이는 버전과 프롬프트가 섞여 있다.
- 비교 도구가 holdout의 점수 바뀐 case를 judge 이유와 함께 출력해, 전체 run 비교 중에 holdout 25건의 이유를 한 번 읽었다. 보정 판단(specific 되돌리기)은 집계 숫자로만 했다.

## 후속 과제

- **#85 생성**: 여는 안내 문장 교체(스펙 결함 23/30), 재료 선택(이미 끝난 일보다 진행 중이거나 다음 달로 이어질 대목, 공통 질문 문장 제외 — ADR 0008의 (b) 코드 필터), 질문은 "했나요"보다 진행 상황을 묻는 쪽. 바꾼 뒤 이 run(g11)을 기준선으로 비교한다.
- **judge 입력에 직전 회차 공통 질문을 넣을지**: (b) 코드 필터가 들어가면 필요 없을 수 있다. 필터 뒤에도 남으면 그때 정한다.
- **잡아내는 능력 재기**: 다음 라벨링에는 판단이 갈릴 만한 메일(규칙·judge가 낮게 본 것, 사람이 고친 운영 메일)을 의도적으로 더 넣고, 시트의 점수 기준에 "스펙 문구는 감점하지 않음", "재료 선택은 별도 체크"를 미리 적는다.
