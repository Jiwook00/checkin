## 컨텍스트

[0003](0003-reminder-eval-dataset.md)에서 고정된 평가셋(211건, 개발용 서브셋 20건)을 만들었다. 이제 이 평가셋 위에서 추출·생성·채점 단계를 올리고, 프롬프트나 모델을 바꿨을 때 품질·비용·지연이 어떻게 달라지는지 비교해야 한다. 그 전에 LLM 품질과 무관하게 먼저 확인할 것이 있다.

1. 같은 평가셋을 같은 방식으로 반복 실행할 수 있는가
2. 실행마다 무슨 입력으로 무슨 출력이 나왔는지 남는가
3. 두 실행의 차이가 프롬프트·모델 때문인지 데이터 때문인지 가려지는가
4. 잘못 돌려도 비용이 무한정 늘지 않는가

제약은 M1 16GB 노트북 한 대와 1인 프로젝트라는 점이다. 이후 단계(P2~P4)가 모두 이 형식 위에 올라가므로, 여기서 정한 인터페이스와 기록 형식이 바뀌면 이후 비교 결과를 이어 볼 수 없다.

## 결정

`scripts/eval/`에 독립 Deno 스크립트로 만든다. 파일은 `llm.ts`(provider), `stages.ts`(단계), `harness.ts`(run · compare), `types.ts`(평가셋 공용 타입)로 나눴다.

### LLMProvider 하나로 Claude · Ollama · echo

`complete({ system, messages, maxTokens, jsonSchema? }) → { text, usage, latencyMs, model, stopReason }` 하나만 두고 세 가지로 구현했다. 같은 단계 코드가 Claude API와 로컬 모델(Ollama)에서 그대로 돌아야 P2의 로컬 비교가 성립한다. `echo`는 호출 없이 입력을 돌려주는 provider라서, 키도 비용도 없이 전체 흐름·상한·비교를 검증할 수 있다.

### 모든 호출은 한 곳을 지난다

단계 코드는 provider를 직접 부르지 못하고 `ctx.call`만 쓴다. 이 한 곳에서 토큰 집계, 상한 검사, 호출 기록이 이뤄진다. 단계가 늘어도 집계가 빠지는 경로가 생기지 않게 하려는 것이다.

### 기록은 case × 단계마다 바로 남긴다

`local/eval/runs/<runId>/`에 세 파일을 둔다.

- `config.json`: 모델, 단가, 단계별 프롬프트 해시, 평가셋 해시(`casesSha256`), 선택한 case 목록, 코드 커밋
- `records.jsonl`: case × 단계마다 입력 해시, 출력, 호출별 토큰·지연·종료 사유, 점수. **끝나는 즉시 한 줄씩 덧붙인다**
- `summary.json`: 종료 상태(`completed` · `stopped_budget` · `failed`), 토큰, 비용, 단계별 통계. 실행이 끝날 때 쓰되 중단돼도 쓴다

`summary.json`만 믿지 않고 `records.jsonl`을 줄 단위로 쓰는 이유는, 중간에 죽어도 그때까지의 기록이 남아야 하기 때문이다.

### 토큰 상한은 호출 전에 검사한다

`누적(입력+출력) + 이번 호출의 입력 추정 + max_tokens`가 `--max-tokens`를 넘으면 호출하지 않고 멈춘다(exit 2). 출력 상한(`max_tokens`)만큼의 여유를 남기고 멈추고, 입력 추정이 실제보다 작으면 이 보장이 깨지므로 추정은 위쪽으로 틀리게 잡는다(아래 결과 참고).

### 비교는 해시부터 본다

`compare`는 두 run의 설정 차이(provider, 모델, 단계별 프롬프트 해시, 평가셋 해시, 코드 커밋)를 맨 위에 보여주고, 평가셋 해시가 다르면 경고한다. 그다음 단계별 점수·토큰·지연·비용 차이와 점수가 바뀐 case 목록을 낸다. 단계별 표는 두 run에서 모두 실행된 case만 쓴다. 상한으로 멈춘 호출은 실행되지 않은 것으로 취급한다.

### 확인용 더미 단계

모델에게 원문 앞 300자를 그대로 출력하게 하고, 완전히 같으면 1점을 주는 `echo` 단계를 하나 둔다. 품질을 재려는 것이 아니라 호출 → 기록 → 채점 → 비교가 끝까지 도는지 보는 용도다. 실제 모델에서 점수가 흔들리기 때문에 `compare`의 "점수가 바뀐 case" 출력이 실제로 검증된다.

## 검토한 대안

### 대안 A: 기존 평가 도구(promptfoo 등)나 LLM 프레임워크를 쓴다

- **장점**: 비교 화면과 채점기 라이브러리가 이미 있다.
- **단점**: 입력 해시·평가셋 해시·추출 결과 캐시처럼 이 프로젝트의 재현성 규칙을 도구 형식에 맞춰야 한다. 또 이번 에픽의 목적이 "평가 시스템을 직접 설계해 본 경험"이라 핵심 부분을 가져다 쓰면 설명할 내용이 줄어든다. 지금 규모(20~211건, 단계 2~3개)에서는 직접 만드는 비용이 작다.

### 대안 B: 호출 후에 상한을 검사한다

- **장점**: 구현이 가장 단순하다. 추정 오차에 영향받지 않는다.
- **단점**: 상한을 한 번의 호출만큼 넘을 수 있다. 입력이 긴 case에서는 그 한 번이 크다. "상한 이내"를 보장하는 쪽이 비용 가드의 의미에 맞다고 봤다.

### 대안 C: run 결과를 SQLite나 DB에 저장한다

- **단점**: 스키마와 마이그레이션이 필요하고, 회고 원문이 들어간 기록이 저장소 밖으로 나갈 위험이 커진다. JSONL은 `grep` · `jq`로 바로 읽히고, `local/`에만 둬서 git에서 제외된다.

### 대안 D: case를 병렬로 실행한다

- **단점**: 누적 토큰으로 상한을 검사할 때 호출 순서에 따라 멈추는 지점이 달라진다. 기록 순서도 흔들린다. 20건 기준으로 순차 실행이 충분히 빠르다(Claude 20건 약 40초). 로컬 모델은 어차피 한 번에 하나씩만 돈다.

## 결과

2026-10-26, 개발용 서브셋 20건, `echo` 단계, Claude `claude-haiku-5-5`로 같은 설정을 두 번 실행했다.

| 항목          |  run A |  run B |
| ------------- | -----: | -----: |
| 입력 토큰     |  4,706 |  4,706 |
| 출력 토큰     |  5,453 |  5,688 |
| 비용 (USD)    | 0.0032 | 0.0033 |
| 지연 p50 (ms) |  1,772 |  1,792 |
| 지연 p95 (ms) |  2,414 |  2,602 |
| `exact` 평균  |   0.65 |   0.70 |

- **`compare`가 차이를 찾아낸다**: 설정은 같은데 점수가 바뀐 case가 3건이었다(1→0 한 건, 0→1 두 건). 점수가 같으면서 출력만 바뀐 기록은 0건이었다. 같은 모델·같은 입력이라도 평가 한 번의 점수를 정답으로 보면 안 되고, 점수 차이를 해석하려면 이 정도의 흔들림(20건 중 3건)을 기준으로 삼아야 한다.
- **점수 0의 원인**: 확인한 3건은 모델이 원문의 오타를 고치거나 마크다운 서식을 바꾼 경우였다. 지시는 "한 글자도 바꾸지 말 것"이었다.
- **입력 토큰 추정을 실측으로 고쳤다**: 처음에는 글자 ÷ 2로 추정했는데(`parse-bench.ts`와 같은 가정), 예상 입력 2,332토큰에 실제 4,706토큰으로 실제가 2.0배였다. 한글은 글자 하나가 토큰 하나에 가깝고, 이 추정이 호출 전 상한 검사에도 쓰이므로 실제보다 작으면 "상한을 넘기지 않는다"는 보장이 깨진다. 호출별로 보면 Claude는 글자 수 + 32토큰 이하, Qwen은 글자 수 이하였다. 그래서 **글자 수 + 요청당 40토큰**으로 바꿨고(cafb755), dry-run 예상 입력이 5,456토큰으로 실제의 1.16배가 됐다. 영어처럼 토큰이 적은 글에서는 더 크게 틀리지만 상한 검사에는 안전한 쪽이다. 같은 상한 4,000으로 다시 실행하면 4건을 끝내고 멈췄고 누적은 3,139토큰이었다. 비용 상한(dry-run $0.0066)은 출력 상한(`max_tokens` 600 × 20)을 모두 쓴다고 가정하므로 실제($0.0032)의 2배쯤으로 나온다.
- **상한 중단**: `--max-tokens 4000`으로 실행하면 5건을 끝내고 6번째 case 호출 전에 멈췄다. 누적은 3,748토큰으로 상한 이내였고, 기록은 6줄(마지막은 `budget_stop`), `summary.json`의 상태는 `stopped_budget`, 종료 코드는 2였다.
- **로컬 모델 (Ollama, `qwen2.5:7b`, M1 16GB)**: 같은 20건을 실행해 `compare`로 Claude와 비교했다. 입력 3,257 · 출력 2,362토큰에 비용은 0, 지연은 p50 17.8초 · p95 25.6초로 Claude(1.8초 · 2.4초)의 약 10배였다. `exact` 평균은 0.70으로 Claude run B와 같았지만 **점수가 다른 case는 11건**이었다. 평균이 같아도 같은 case를 맞힌 것은 아니므로, 모델을 비교할 때는 평균이 아니라 case별 차이를 봐야 한다.

## 알려진 한계

- **dry-run은 앞 단계 출력 크기를 모른다.** 호출 없이 파이프라인을 돌리기 때문에, 뒤 단계의 입력에 앞 단계 출력이 들어가는 경우(P2의 추출 → 생성) 그 부분이 추정에서 빠진다.
- **입력 토큰 추정은 한글 20건 실측으로 맞췄다.** 글자 수 + 요청당 40토큰은 이 서브셋(한글, 300자 안팎)에서 Claude와 Qwen 모두 실제 이상이었다. 다른 모델이나 훨씬 긴 입력에서는 달라질 수 있어, P2에서 새 모델을 붙일 때 dry-run 추정과 실제 입력을 다시 비교한다. 이 추정은 `echo` 단계의 입력 길이에서 맞춘 값이다.
- **Claude 단가 표는 모델마다 직접 추가해야 한다.** 모르는 모델은 실행 전에 멈춘다. 채점용 상위 모델은 P3에서 추가한다.
- **실행은 순차다.** 211건 전체와 로컬 모델을 함께 쓰면 오래 걸린다. 필요해지면 그때 병렬화를 다시 본다.
- **채점기는 아직 더미 하나뿐이다.** 규칙 채점기와 LLM 채점기는 #76에서 만든다.
- **Ollama는 Qwen 2.5 7B로만 확인했다.** P2에서 비교할 다른 모델은 같은 인터페이스로 꽂을 수 있지만 검증하지 않았다.
