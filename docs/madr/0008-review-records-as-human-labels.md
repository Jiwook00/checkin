# 0008 - 운영 검토 기록을 사람 라벨로: 한 회차를 끝까지 돌려 고리를 닫는다

- 상태: 승인됨
- 날짜: 2026-11-02
- 관련 이슈: #84 (에픽 #72)
- 관련 커밋: ba5f653, bbab57a, 9e33d4e, afc9736
- 이전 결정: [0006 - 생성·채점기](0006-generation-graders.md), [0007 - 관리자 화면과 초안 생성 API](0007-admin-reminder-drafts.md)

## 컨텍스트

ADR 0007로 평가한 코드가 운영에서 돈다. 남은 절반은 반대 방향이다. 운영에서 사람이 승인·수정·반려한 기록이 다시 평가 데이터가 되어야 한다. 그래야 #77(judge와 사람 판단 비교)이 합성 입력이 아니라 실제 메일로 잴 수 있다.

이번 단계는 2026-10 회차를 검토부터 발송까지 끝내고, 그 기록을 하네스가 읽는 파일로 내보낸다. 답할 질문은 셋이다.

1. 검토 기록의 어떤 row를, 어떤 분모로 세는가 (재생성, 발송하지 않은 멤버)
2. 자유 텍스트인 검토 사유를 judge의 0/1/2 항목과 어떻게 잇는가
3. "보냈다"는 사실을 어디에 남기는가

## 결정

### 실제 한 회차는 기존 초안 그대로, 재생성은 반려한 멤버만

2026-10 회차는 ADR 0007의 첫 운영 실행에서 만든 초안을 그대로 검토하고 보냈다. 전부 다시 생성하면 같은 코드로 흔들림만 늘고 첫 검토 기록과 이어지지 않는다. 반려한 멤버만 화면의 "다시 생성"으로 새 row를 만든다.

### 분모는 둘: 발송 단위와 생성 단위

- **발송 단위**: 멤버별 최신 row(최종 row). 승인·수정·반려와 발송 여부를 여기서 센다.
- **생성 단위**: 회차의 모든 row를 첫 생성과 재생성으로 나눈다. 구분 기준은 생성 시각이 아니라 "멤버별 첫 row인가"다. 재생성은 추출을 재사용(`extract.reusedFrom`)하므로 토큰·지연을 따로 적는다.
- **발송 대상 아님**(`not_target` 태그)은 품질 분모에서 뺀다. 메일 내용과 무관하게 운영자가 발송 대상에서 뺀 멤버라 품질 판단이 아니다. 이번 회차에 1건 나왔고, 시드 태그에 없어 새 유형으로 추가했다.

### 검토 기록은 두 파일로 나눈다

| 파일               | 만드는 쪽                                 | 내용                                                           |
| ------------------ | ----------------------------------------- | -------------------------------------------------------------- |
| `reviews.json`     | `eval-dataset.ts --reviews` (DB SELECT만) | drafts row를 가공 없이 옮김. 회고 원문 대신 `retroId`+`sha256` |
| `review-tags.json` | 사람 (사유·수정 diff를 읽고)              | row별 유형 태그와 메모. 태그마다 연결된 judge 항목             |

둘 다 `local/eval/dataset/`에 둔다(git 제외, 메일 본문 포함). 하네스는 DB에 접근하지 않고 이 파일만 읽는다. 지표 요약(`reviews-summary.md`)에는 멤버 이름과 사유 원문이 없어서 PR에 그대로 붙인다.

### 사유는 시드 태그로 묶어 judge 항목과 잇는다

태그를 붙이기 전에 목록을 고정했다. 표본이 8통 안팎이라 사유에서 귀납하면 건마다 태그가 하나씩 생겨 #77과 연결되지 않는다.

| 태그                | 정의                                               | 연결 judge 항목     |
| ------------------- | -------------------------------------------------- | ------------------- |
| `common_q_material` | 직전 회차 공통 질문(또는 그 답)을 콜백 재료로 고름 | judge 밖 (ADR 0007) |
| `goal_check`        | 이행 확인 투                                       | tone                |
| `premise_outside`   | 질문·콜백의 전제가 재료 밖                         | grounded            |
| `generic`           | 누구에게나 할 수 있는 말                           | specific            |
| `form`              | 형식(문장 수·구간 구성)                            | 규칙 채점기 `form`  |
| `tone_other`        | 그 밖의 톤 문제                                    | tone                |
| `notice`            | 공지·일정 문구                                     | judge 밖            |
| `not_target` (새)   | 발송 대상 아님. 품질 분모에서 제외                 | judge 밖            |

### 사람 판단은 화면 상태가 아니라 태그로 센다

라벨 정의: 승인 = 문제 없음(전 항목 통과), 수정 = 태그가 붙은 항목만 문제, 반려 = 태그 항목은 0점에 해당.

다만 이번 회차에서 화면 상태와 실제로 보낸 메일이 달랐다. 화면에서 승인한 2통도 발송할 때 여는 문장을 고쳤고, 수정 승인 5통도 `edited_mail`에는 문장 삭제만 있고 보낸 메일에는 대체 문장이 들어갔다. 그래서 태그가 있으면 태그로(태그 하나라도 있으면 "문제 있음"), 없으면 화면 상태로 센다. 승인 row에도 태그를 붙일 수 있다. DB의 상태는 고치지 않는다(운영 기록을 그대로 둔다).

### 발송 기록은 DB 컬럼에 둔다

`checkin_reminder_drafts.sent_at`·`sent_via`(`manual` | `api`). 화면에 복사와 분리된 "발송함으로 표시" 버튼을 둔다. 복사했다고 보낸 것은 아니다.

- 제약: 두 컬럼은 함께 채운다. 승인·수정 승인 row만 발송 표시할 수 있고, 보낸 뒤 draft·반려로 되돌릴 수 없다. 한 회차 한 멤버에 발송 기록은 하나다(부분 unique 인덱스).
- 로컬 파일이 아니라 DB에 둔 이유: 메일 API 발송(#85)으로 넘어가면 기록하는 쪽이 코드가 된다. 중복 발송도 DB가 막아야 한다.

### 반려한 초안은 되돌리지 않고 다시 생성한다

`status: "draft"`로 되돌리면 `edited_mail`·`review_note`·`reviewed_at`이 지워져 사람 라벨이 사라진다. 첫 운영에서 실제로 반려 사유 하나가 이렇게 유실됐다. 화면에서 반려·발송된 초안의 "다시 검토"를 막고, 반려는 "다시 생성"으로 안내한다.

## 검토한 대안

- **기존 초안을 전부 재생성**: 같은 코드라 얻는 정보가 없고, 첫 검토 기록과 끊긴다.
- **사유를 귀납으로 분류**: 표본이 작아 태그가 사유 수만큼 생기고 judge 항목과 이어지지 않는다.
- **발송 기록을 로컬 파일에**: 자동 발송으로 넘어가면 쓸모가 없고, 중복 발송을 막지 못한다.
- **`reviewDraft` 되돌리기 허용**: 라벨이 덮어써진다. 되돌려야 할 때는 새 row를 만든다.
- **이미 보낸 9월 회차를 소급 생성해 표본 늘리기**: 이미 회고를 쓴 멤버는 생성 대상이 아니어서 실제 발송 대상과 달라지고, 보내지 않은 메일에 붙는 라벨이라 운영 라벨이 아니다. 표본은 #77에서 하네스 출력에 라벨을 붙이는 방식으로 늘린다.

### 규칙 채점 × 사람 판단 (분모 = 품질 대상 최종 row 7)

|                | 문제 없음 | 문제 있음 | 합계 |
| -------------- | --------: | --------: | ---: |
| 규칙 채점 걸림 |         0 |         0 |    0 |
| 규칙 채점 통과 |         0 |         7 |    7 |

ADR 0007 첫 운영 실행의 "규칙 채점 걸림 + 반려" 1건은 여기 없다. 그 row와 첫 재생성 row는 운영자가 화면 동작을 시험하던 단계의 row라 라벨에서 뺐고, 최종 row만 센다.

### 해석: 평가와 같았던 것

- **근거·구체성 실패가 없었다.** `premise_outside`·`generic`·`goal_check` 0/7. 하네스 judge 점수(grounded·specific 0.946)와 방향이 같다.
- **형식은 규칙 채점기와 사람이 일치했다.** 최종 row에서 둘 다 문제를 보지 않았다.
- **콜백 없는 메일(4/7)은 여는 문장 말고 손댄 곳이 없었다.** 라벨 가치가 작다는 ADR 0007의 예상과 같다.

### 해석: 평가와 달랐던 것

- **`tone_other` 7/7은 메일별 실패가 아니라 스펙의 결함이다.** 생성 프롬프트가 opening에 "회고를 이제 쓸 수 있다는 사실을 알린다"고 지시했고, 모델은 그대로 따랐다. 사람은 이 문장을 모든 메일에서 빼거나 다른 문장으로 바꿨다. judge는 스펙에 맞는지를 보므로 구조적으로 이것을 잡지 못한다(하네스 tone 0.975). 모든 메일이 같은 문장이라 메일 한 통씩 보는 평가에서는 눈에 띄지 않았다.
- **`common_q_material`은 공통 질문의 답이 아니라 질문 문장 자체였다.** 콜백 있는 메일 3통 중 2통에서 추출 재료의 evidence가 직전 회차 공통 질문 문장과 글자 그대로 같았다(회고 본문에 질문을 옮겨 둔 대목). 추출은 그것을 멤버의 goal·moment로 읽었고, 생성은 그중 1통에서 콜백으로 골랐다. 재생성은 추출을 재사용하므로 같은 재료 목록에서 같은 실패가 반복됐고, 사람이 손으로 고쳤다.
- **사람은 judge 기준에 없는 시의성도 봤다.** 위 메일을 고칠 때 "그 달에 예정됐던 일"을 콜백으로 바꿨다. 새 태그로 만들지는 않았다(1건).
- **화면 상태와 보낸 메일이 달랐다.** 위 "사람 판단은 태그로 센다"의 이유다.

## 알려진 한계

- **표본이 작다.** 품질 대상 7통, 콜백 있는 메일 3통이다. 비율은 방향만 보여 준다.
- **태그는 한 사람(운영자)이 붙였다.** 일치도를 잴 두 번째 평가자가 없다.
- **보낸 본문이 DB에 없다.** 발송할 때 화면 밖에서 고친 문장은 `edited_mail`에 없고, 태그 메모로만 남는다. 메일 API 발송(#85)으로 화면이 보낸 본문을 기록하면 해소된다.
- **초기 시험 row 2건은 라벨에서 뺐다.** 그중 첫 반려는 사유가 "다시 검토"로 지워졌다(ADR 0007에 요약이 있다).
- **콜백 없는 메일은 라벨 가치가 작다.** 이번 회차에서는 스펙 결함 하나만 드러냈다.

## 후속 과제

- **#77 judge vs 사람**: 이번 최종 row 7건에 judge를 돌려 태그와 비교한다. 스펙 결함(모든 메일 공통)과 메일별 실패를 나눠 센다. 나누지 않으면 tone 일치도가 결함 하나로 결정된다. 시의성을 judge 기준에 넣을지 함께 정한다. 표본은 하네스 출력에 같은 태그 체계로 라벨을 붙여 늘린다(출처를 운영 라벨과 구분). → [ADR 0009](0009-human-judge-agreement.md)
- **공통 질문 재료 대응 (ADR 0007의 (a)/(b))**: (b) 코드 필터를 먼저 한다. 이번 사례는 evidence가 질문 문장과 글자 그대로 같아, 정규화 후 포함 여부만 봐도 2/2를 걸러낸다. 추출 프롬프트가 그대로라 추출 기준선과 호출 캐시가 유지된다. 질문 없이 답만 적은 경우는 (b)로 못 잡으므로, 그런 사례가 나오면 (a)를 검토한다.
- **여는 문장**: 사람이 보낸 문장을 템플릿 고정 문구(코드)로 옮기거나 프롬프트 지시를 바꾼다. 어느 쪽이든 생성 요청이 바뀌어 v3 기준선이 끊기므로 #85와 함께 한다.
- **#85 범위 확장**: 메일 API 발송(보낸 본문 = 기록), 발송 대상 여부(정규 참여 표시 등으로 생성 전에 거름), 콜백 없는 메일 4/7에 대한 결석 분기·반응 블록.
