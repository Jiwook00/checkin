# 0006 - 사실은 코드가, 말은 LLM이 쓰고, 채점은 흔들림을 분해해서 읽는다

- 상태: 승인됨
- 날짜: 2026-10-28
- 관련 이슈: #76 (에픽 #72)
- 관련 커밋: e7118d8, 9c2881f, 2a21f85, 7eef1df, bed3886, 844ccc3, 402f5d8
- 이전 결정: [0003 - 평가셋](0003-reminder-eval-dataset.md), [0004 - 평가 하네스](0004-eval-harness.md), [0005 - 추출·근거·로컬](0005-extraction-evidence-local-models.md)

## 컨텍스트

#75에서 회고 원문에서 콜백 재료를 뽑고 근거를 코드로 검증하는 데까지 만들었다. 이번 단계는 그 재료로 리마인더 메일 본문을 생성하고, 생성 결과를 잰다.

답할 질문은 셋이다.

1. 메일의 어느 부분을 LLM에게 맡길 것인가
2. 생성 결과를 무엇으로, 얼마의 비용으로 잴 것인가 (형식은 코드로 잴 수 있지만 "이 사람에게만 보낼 수 있는 질문인가"는 코드로 잴 수 없다)
3. 프롬프트를 고친 뒤 점수가 바뀌었을 때, 그게 진짜 변화인지 어떻게 가릴 것인가 (생성도 채점도 흔들린다)

## 결정

### LLM은 말이 필요한 네 구간만 쓰고, 일정·링크는 코드가 붙인다

메일은 다섯 구간이다. LLM은 인사(opening), 콜백(callback), 공통 질문 소개(commonQuestion), 맺음(closing)을 JSON으로 쓰고, 공지(일정·투표 링크·장소)는 코드가 붙인다. LLM은 일정 정보를 아예 보지 않는다.

- 8월에 실제 발송한 메일을 뜯어 보면 사람이 다듬은 부분은 콜백이고, 일정·투표 안내는 데이터 그대로였다. 날짜를 LLM이 쓰게 하면 틀린 날짜나 "며칠 남았어요" 같은 카운트다운이 생길 수 있는데, 코드로 붙이면 그 실패가 구조적으로 사라진다.
- 출력 스키마는 필드 순서가 생성 순서다. 콜백 재료 번호(`callbackItem`)를 먼저 고르고 그다음 문장을 쓴다. "없음"은 nullable 대신 `0`과 빈 문자열로 표현한다.
- 생성 입력에는 #75의 근거 검증을 **통과한 항목만** 넣는다. 통과한 항목이 0개면 콜백 없이 쓴다. 정답 라벨(`expectCallback`)은 생성 입력에 넣지 않고 채점기만 본다.

### 채점은 두 층이다: 규칙(코드, 매번) + LLM(콜백이 있을 때만)

| 채점기                                       | 방식             | 재는 것                                                                                      |
| -------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------- |
| `json` · `callback_match` · `callback_label` | 코드             | 파싱, 재료 유무와 콜백 유무가 맞는가, 정답 라벨과 맞는가                                     |
| `form`                                       | 코드             | 구간별 문장 수, 공통 질문 원문 그대로 포함, 콜백의 후속 질문, LLM 구간에 날짜·시간·링크 없음 |
| `banned`                                     | 코드             | 카운트다운, 도서관·사서 비유, 비교·분량 압박, 느낌표·이모지, 프롬프트 예시 유출              |
| `voice`                                      | 코드             | 말끝이 "~니다"인 문장 (고정 문형 "지난 회고 잘 읽었습니다." 하나만 허용)                     |
| `grounded` · `specific` · `tone`             | LLM (Sonnet 5.5) | 재료에 있는 사실만 말하는가, 이 사람에게만 보낼 수 있는가, 담백하고 부담 없는가              |

- 규칙 채점기는 실패 사유를 `[구간] 태그:"내용"`으로 남겨 유형별로 셀 수 있게 했다. 콜백 구간의 금지 표현은 회원 원문에 같은 낱말이 있으면 허용한다(원문의 "대출"을 짚는 것은 비유가 아니다).
- LLM 채점은 호출이 필요해서 채점 함수가 아니라 별도 **단계**로 두었다. 그래서 단계별 비용 표에서 채점이 한 칸으로 잡힌다.
- 항목마다 `reason`을 `score`보다 먼저 쓰게 했다. #75에서 evidence를 text보다 먼저 쓰게 한 것과 같은 원리로, 근거를 먼저 쓰고 점수를 맞추게 한다.
- 척도는 0/1/2다. 단계가 적을수록 같은 글에 같은 점수가 나오기 쉽고, 사람 라벨(#78)과 비교하기 쉽다.
- 콜백이 없는 메일은 LLM이 채점하지 않는다. 그런 메일의 톤은 규칙 채점기가 맡는다.

### LLM 채점은 `claude -p`(구독)로 돌린다

API로 Sonnet 채점을 하면 계획 전체가 약 $10, Opus면 $35~45였다. 비용 거의 전부가 "강한 모델이 메일을 읽는 값"이다. Claude Code 헤드리스 모드(`claude -p`)는 구독 사용량으로 돌아 호출당 과금이 없고, Sonnet·Opus를 그대로 쓸 수 있어 "생성(Haiku)보다 강한 모델로 채점한다"는 원칙을 지킨다. 하네스의 provider 인터페이스에 provider 하나를 더 끼우는 일이었다.

- **`--safe-mode`가 필요했다.** `--system-prompt`만 주면 전역 CLAUDE.md(사용자 이름·프로젝트 목록)가 입력에 그대로 들어왔다(1,381 vs 262토큰). `--bare`는 OAuth를 읽지 않아 쓸 수 없었다.
- **모델은 전체 ID로 준다.** `--model sonnet` 별칭이 5.5가 아닌 다른 버전으로 풀렸다.
- 환경 변수에서 API 키를 지운 채 실행해, 구독 로그인이 없으면 API로 새지 않고 실패하게 했다.
- 거절·잘림은 `judge_json=0`으로 기록한다. fallback 모델은 쓰지 않는다. 채점 모델이 조용히 바뀌면 채점이 섞인다.
- 실제 청구가 없으므로 단계 비용은 **API 환산**(고정 단가 × 채점 모델 토큰)으로 따로 기록한다.

**LLM 채점은 개발용이다.** 프롬프트·모델을 바꿀 때 평가 하네스에서만 돈다. 매달 운영 흐름(추출 → 근거 검증 → 생성 → 사람 검토 → 발송)에는 LLM 채점이 없고, 운영 비용은 Haiku 추출·생성 8통에 월 약 $0.01이다.

### 튜닝과 홀드아웃을 나눈다

#75에서 준-홀드아웃이 깨진 교훈으로, 평가셋 211건을 **tune 40건**(dev 20 + callback 20, 시드 고정)과 **holdout 171건**으로 나눴다. 프롬프트·채점 기준을 고치려고 출력과 채점 이유를 읽는 것은 tune에서만 했다. holdout은 기준선과 최종 때 집계 숫자와 실패 태그만 봤다. `cases.json`은 바꾸지 않고 서브셋 파일만 더해 비교의 연속성(해시)을 지켰다.

### 흔들림을 분해해서 읽는다

하네스에 단계별 캐시 읽기(`--cache extract,generate`)를 더해, 같은 글을 다시 채점하거나(채점 흔들림) 같은 재료로 다시 생성(생성+채점 흔들림)할 수 있게 했다. 개선 회차의 변화는 이 흔들림 폭과 견줘서 읽었다.

### 채점 기준을 고친 것과 답변을 고친 것을 나눠 기록한다

v1의 떨어진 case를 읽고 유형마다 "답변을 고칠지, 채점 기준을 고칠지"를 정했다. 채점 기준을 고친 것은 따로 커밋하고, 캐시로 **같은 답변을 다시 채점**해 "점수만 바뀐 것"을 분리했다.

- 채점 수정: 콜백의 끝문장이 대부분 "~는지 궁금해요" 같은 간접 의문이었다. 의미상 후속 질문이고 사람이 쓴 8월 메일도 같은 문형을 쓴다. `?`만 질문으로 보던 기준이 과했다. 또 LLM 채점기가 스킬의 고정 문형("지난 회고 잘 읽었습니다")을 형식적인 인사로 감점하고 있어서, 정해진 문형은 감점하지 않는다고 명시했다. 말끝 섞임을 잴 `voice`를 더했다.
- 답변 수정: 투표 부탁, 이행 점검 투의 질문, 누구에게나 할 수 있는 근황 질문, 시제가 바뀐 인용, 말끝 섞임.

### 프롬프트는 v3를 쓰고, 개선은 거기서 멈춘다

v2는 질문을 구체적으로 묻게 하고 투표 부탁을 막고 말끝을 "~해요"로 맞췄다. v3는 v2가 새로 만든 실패를 겨냥했다. 질문의 전제를 고른 재료의 evidence 안으로 제한하고, v2 프롬프트의 한 구절("무엇이 달라졌는지")이 새 질문 틀로 굳은 것을 없앴다. 두 회차 모두 예시 문장은 넣지 않았다.

v4는 하지 않았다. 남은 실패 둘은 프롬프트로 풀리지 않는다는 근거가 v2·v3에 있다(아래 결과·한계). tune에서 judge 평균의 회차 간 차이가 흔들림 바닥에 닿아, 더 고치면 tune 40건에 과적합될 위험이 커졌다.

## 검토한 대안

### 대안 A: 다섯 구간 전부 LLM이 쓰고 채점기가 날짜·링크를 검사한다

- **단점**: 지어낼 여지를 남긴 뒤 잡는 구조다. 코드가 붙이면 그 실패가 생길 수 없다. 대신 LLM 구간에 날짜·시간·링크가 없어야 한다는 규칙(`form`)만 남겼다.

### 대안 B: 콜백만 LLM이 쓰고 나머지는 고정 템플릿

- **단점**: 인사·맺음이 매달 같은 문장이 된다. 이번 결과를 보면 고정 문형("지난 회고 잘 읽었습니다")조차 LLM이 바꾸는 일이 있어, 콜백 첫 문장 정도는 코드로 붙이는 게 맞을 수 있다(후속 과제).

### 대안 C: Sonnet·Opus API로 채점한다

- **장점**: 지연이 API 기준이라 비교 가능하고, CLI 버전에 묶이지 않는다.
- **단점**: 계획 전체 Sonnet 약 $10, Opus 약 $35~45. 실제 청구는 Haiku 생성 몇 센트뿐인데 채점이 비용의 대부분을 차지한다. 실제 API 환산 비용도 전체 run 1회 채점이 $2.0으로, 생성($0.08)의 25배였다.

### 대안 D: Haiku·로컬 모델로 채점한다

- **단점**: Haiku는 생성 모델과 같아 자기 채점 편향이 크고, 로컬 모델(#75의 Gemma 4)은 생성 모델보다 약하다. 채점은 생성보다 강한 모델이 해야 한다.

### 대안 E: 0~10 척도

- **단점**: 단계가 많을수록 같은 글에 다른 점수가 나오기 쉽다. 3단계에서도 같은 글을 다시 채점하면 93항목 중 11~14개가 바뀌었다.

### 대안 F: dev 20건만으로 튜닝한다

- **단점**: dev 중 콜백이 있는 case는 12건이라 흔들림에 묻힌다. tune 40건(콜백 31건)으로도 judge 평균의 회차 간 차이는 가를 수 없었다(아래 결과).

## 결과

2026-10-27~28, 생성 Haiku 5.5(추론 끔), 채점 Sonnet 5.5(`claude -p --effort low`, Claude Code 2.1.311). 추출은 #75 v1을 처음 한 번 부르고 이후는 캐시로 고정했다. LLM 채점 평균은 콜백이 있는 case만이다(n 표기).

### 흔들림 분해 (tune 40건, 채점 31건 × 3항목 = 93항목)

| 비교                                         | 바뀐 judge 항목 | 평균 차이                    |
| -------------------------------------------- | --------------: | ---------------------------- |
| 같은 글, 같은 채점기, 2회 (채점 흔들림)      |           11~14 | ±0.03                        |
| 같은 재료, 생성·채점 새로 (생성+채점 흔들림) |           23~28 | specific −0.064, tone −0.048 |
| 같은 글, Claude Code 2.1.209 vs 2.1.311      |              32 | ±0.03                        |
| 같은 글, Sonnet vs Opus 채점                 |   12 (일치 87%) | Opus +0.03                   |

- **Claude Code 버전이 채점 점수를 바꿨다.** 같은 모델 ID인데 버전만 달라도 같은 버전 두 번(11~14)보다 훨씬 많이 바뀌었다. 2.1.311은 safe-mode에서도 환경 정보를 호출마다 얹어 채점 입력이 약 2,500 → 4,100토큰으로 늘었다. 그래서 2.1.209로 잰 기준선은 버리고 2.1.311로 다시 쟀고, 실험 중에는 업데이트를 막았다.
- **Sonnet–Opus 일치도**: grounded 31/31, specific 27/31, tone 23/31. 가장 판단이 갈리는 항목은 tone이다. Opus가 약간 후하다. 지연(p50 5.9초 vs 8.9초)과 API 환산 비용(0.47 vs 0.85달러)을 보면 Sonnet을 유지할 이유가 충분하다.

### 채점 기준 수정 효과 (같은 답변을 다시 채점)

| 채점기   | 옛 기준 | 새 기준 |
| -------- | ------: | ------: |
| form     |   0.350 |   1.000 |
| voice    |       - |   0.325 |
| specific |   0.935 |   0.855 |
| tone     |   0.903 |   0.968 |

`form` 실패 26건 중 25건이 후속 질문 판정이었다. 답변은 하나도 바뀌지 않았는데 형식 통과율이 0.35에서 1.0이 됐다. 전체 211건 v1 실행에서도 `form` 실패 120건 전부가 같은 원인이었다. 채점 기준이 틀리면 개선 대상을 잘못 고른다. 이 단계에서 프롬프트를 "질문 부호를 붙여라"로 고쳤다면 실제 문제(질문이 사람마다 같은 틀)는 그대로였을 것이다.

### 개선 회차 (tune)

| 프롬프트                       |  form | voice | grounded | specific |  tone | 바뀐 judge 항목 (직전 대비) |
| ------------------------------ | ----: | ----: | -------: | -------: | ----: | --------------------------: |
| v1 (새 채점 기준)              | 1.000 | 0.325 |    0.968 |    0.855 | 0.968 |                           - |
| v2                             | 0.975 | 1.000 |    0.919 |    0.919 | 0.952 |                          23 |
| v3                             | 1.000 | 1.000 |    0.903 |    0.903 | 0.919 |                          21 |
| v3 (최종 전체 run의 tune 부분) | 0.975 | 1.000 |    0.935 |    0.968 | 0.952 |                           - |

- **결정적인 변화만 확실했다.** `voice`는 0.325 → 1.0. v3에서 "달라진 점" 질문 틀은 31건 중 13건(정규식) → 1건, 고정 문형 변형은 2 → 5건으로 늘었다. 셋 다 사람이 출력을 읽고 센 것이고, judge 평균에는 드러나지 않았다.
- **judge 평균은 tune에서 회차를 가르지 못했다.** 같은 v3 프롬프트로 생성만 다시 한 두 run의 specific이 0.903과 0.968로, v2의 개선폭(+0.064)만큼 달랐다. 바뀐 항목 수도 매 회차 생성+채점 흔들림(23~28) 안이었다.
- **떨어진 case의 유형은 바뀌었다.** v1의 감점 사유는 "누구에게나 할 수 있는 근황 질문"과 "형식적 인사·투표 재촉"이었다. v2부터는 "질문의 전제가 재료 밖에 있다"가 주된 사유다. 구체적으로 물으라고 하자 구체적인 전제를 지어냈다.

### 기준 답안 비교

dataset의 기준 답안 4건(7월 메일)과 8월 실제 발송 메일 5건을 v1·v3 생성 결과와 나란히 보는 리포트를 만들었다(`local/`에만, 회고 원문 포함). 8월 사람 답안 5통은 규칙 채점기를 모두 통과하고, 한 통만 콜백이 4문장이라 `form`에서 벗어난다. 사람도 "한 대목 + 한 질문"에서 살짝 벗어나는 셈이라 범위(2~3문장)는 그대로 두었다. 7월 메일 4통은 지금 금지된 사서 비유에 걸린다.

## 알려진 한계

- **judge tone은 정중한 이행 확인을 잡지 못한다.** goal 재료를 고른 콜백에서 "어디까지 ~하고 계세요", "지금도 ~하고 계세요" 같은 질문이 v2에서 4/15, v3에서 6/10 나왔다. 프롬프트가 금지했는데도 나왔고, 채점기는 이 질문들에 모두 tone 만점을 줬다. 스킬이 가장 먼저 금지하는 "검사하는 투"를 지금 채점 체계는 재지 못한다.
- **질문의 전제가 재료 밖으로 나간다.** 생성 입력에는 evidence(원문 인용)와 요약(text)이 같이 들어간다. v3가 "짚는 내용은 evidence에서만"을 명시했는데도 같은 case에서 요약에만 있는 사실을 짚는 오류가 반복됐다.
- **채점이 Claude Code 버전에 묶인다.** 버전이 바뀌면 같은 글의 점수가 바뀐다. config에 CLI 버전을 남기지만 run 도중 업데이트되면 기록되지 않는다. 사용자 이메일 한 줄은 safe-mode에서도 채점 입력에 남는다(채점에 영향 없음).
- **같은 Claude 계열이 생성과 채점을 한다.** 자기 선호 편향이 있을 수 있다. Sonnet–Opus 교차 채점은 "채점기끼리 같은가"만 보여 준다. 사람 라벨과의 일치는 #78에서 본다.
- **반응(이모지·댓글)과 결석 분기(A~D)는 평가셋에 없어** 이번 생성 범위 밖이다. 공통 질문과 투표 상태는 case id 해시로 고른 합성 입력이다.
- **콜백 없는 메일(전체 211건 중 71건)은 LLM이 채점하지 않는다.** 규칙 채점기만 본다.
- **tune에서 출력을 읽은 사람(모델)이 판단과 수기 집계를 했다.** "달라진" 질문, 고정 문형 변형, 이행 확인 건수는 정규식 후보를 읽고 센 값이라 기준이 엄밀하지 않다.

## 후속 과제

- **생성 입력에서 요약을 빼거나 2단계로 나눈다.** 재료 번호 고르기에는 요약을 쓰고, 문장 쓰기에는 고른 항목의 evidence만 준다. "사실은 코드가 맡는다"의 다음 단계다.
- **고정 문형은 코드가 붙인다.** 콜백 첫 문장("지난 회고 잘 읽었습니다.")을 LLM이 쓰지 않으면, 말끝 규칙과 고정 문형이 부딪혀 생기는 변형이 사라진다.
- **이행 확인을 재는 채점을 만든다.** judge tone 기준에 goal 이행 확인을 명시하거나, 문형 규칙 채점기를 둔다. 기준을 바꾸면 이전 run과 비교가 끊기므로, 바꿀 때 기준선 재채점을 함께 한다.
- 운영에서 규칙 채점기(코드, $0)를 사람 검토 전 점검으로 붙일지는 P6에서 정한다.
