# 갈피 개별 리마인더 생성

> **관리자 화면으로 대체됨 (이슈 #79).** 리마인더 초안은 이제 앱의 `/admin/reminders`(관리자 전용)에서 만든다: ① 공통 질문 승인 → ② 초안 생성(Edge Function + Claude API) → ③ 검토(승인·수정·반려, 복사). 생성 코드는 평가 하네스와 같은 모듈이라 측정한 코드가 곧 운영 코드다. 사용자가 이 스킬을 부르면 **절차를 실행하지 말고** 이 사실을 먼저 알리고 관리자 화면을 안내한다.
>
> 이 문서는 갈피의 톤 규칙·개인 콜백·체크리스트의 **원본(채점 기준의 출처)**으로 남긴다. 화면 v1이 아직 다루지 않는 것 — 받은 반응(이모지·댓글) 블록, 결석 분기 B~D별 본문, HTML 템플릿 — 은 후속 이슈(#85)에서 옮긴다. 그 전에 그런 메일이 필요하면 사용자에게 먼저 묻는다.

체크인 회고 모임의 사서 페르소나 **갈피**가 **모임 전에** 보내는 **개별 맞춤 리마인더**(HTML)를 만든다.
발송 시점은 매번 달라지므로 **본문에서 남은 날짜를 세지 않는다**(§톤 규칙).
**멤버 한 명당 한 통**을 따로 만든다. 발송은 하지 않는다 — 사용자가 프리뷰를 검토한 뒤 직접 보낸다.

**갈피의 목소리 규칙은 [`docs/galpi-letter-guide.md`](../../../docs/galpi-letter-guide.md) §8이 단일 출처다.**
자기지칭·말끝·**사서 메타포 금지**가 거기 있고, 갈피 편지 전 종류에 똑같이 적용된다.
이 스킬에는 개별 리마인더에만 해당하는 규칙만 적는다. 충돌하면 가이드가 우선.

## 다이제스트와 뭐가 다른가

|            | 다이제스트 (`galpi-letter`) | 개별 리마인더 (이 스킬)        |
| ---------- | --------------------------- | ------------------------------ |
| 타이밍     | 모임 **후**                 | 모임 **전** (시점 고정 아님)   |
| 수신자     | 전원 동일 내용              | 멤버별 다른 내용               |
| 목적       | 이번 달 글 모아 보여주기    | 아직 안 쓴 사람 쓰게 하기      |
| 결과물     | `digest-N.html` 1개         | `reminder-{nickname}.html` N개 |
| 마스트헤드 | `No.NN` 번호 있음           | 번호 없음 (연재물 아님)        |

**개별 메일이라는 게 티가 나야 한다.** 전체 공지를 이름만 바꿔 넣은 것처럼 읽히면 이 메일은 실패다.
동시에, 남과 비교하거나 안 쓴 걸 지적하는 순간에도 실패한다. 이 둘 사이가 이 스킬의 전부다.

## 인자

`<session>` (예: `2026-08`) — **회고 세션**을 받는다. 없으면 어느 달인지 묻는다.
선택 `--member <nickname>` — 특정 한 명만 다시 만들 때.
선택 `--dry` — HTML 없이 멤버별 개인화 내용 요약만 출력해서 사용자가 먼저 검토.

### ⚠️ 세션 라벨과 모임 날짜는 서로 다른 축이다

`checkin_retrospectives.session`(회고 세션)과 `checkin_vote_polls.session`(투표 세션)은 **한 달씩 어긋난다.**
예: 회고 세션 `2026-07`의 글들은 2026-08-06~08에 작성됐고, 그 모임은 투표 세션 `2026-08`(확정일 2026-08-08)이었다.

- `<session>` 인자 = **회고 세션**(사람들이 쓸 글의 라벨).
- 모임 날짜는 **그다음 달 투표 세션**의 `confirmed_date`에서 가져온다.
- 헷갈리면 추측하지 말고 사용자에게 "이번 리마인더가 겨냥하는 모임은 N월 N일 맞나요"라고 확인한다.

## 절차

1. **가이드 §8(갈피 목소리) 읽기** — 톤이 이 메일의 핵심이라 매번 읽는다.

2. **이번 회차 공통 질문 확정** — 메일과 앱(글 등록 화면·홈 배너)이 같은 질문을 쓴다. 단일 출처는 DB `checkin_session_questions`(회고 세션당 하나, approved만 노출).

   - 관리자 화면 `/admin/reminders` ①에서 정한다: 이미 쓴 질문 보기, 후보 뱅크에서 고르기, 직접 입력, 선택적 LLM 제안(Haiku, 후보 3개 + 이유), 승인. 승인하는 순간 앱 멤버에게 보인다.
   - `<session>`에 approved 질문이 있으면 그대로 쓴다.
   - **후보 규칙:** 후보 뱅크(`docs/retro-writing-participation.md` §4-2)에서 고르거나 비슷한 결로 만든다. ① 이미 쓴 질문과 겹치지 않는다 ② 한 줄로 답해도 완성되는 가벼운 질문 ③ 개발·성과가 아니라 안부의 온도 ④ 정답이 있거나 평가가 되는 질문은 쓰지 않는다 ⑤ "~는?"으로 끝나는 짧은 한 문장.

3. **데이터 뽑기**

   ```bash
   node scripts/export-reminder-data.mjs <session>
   ```

   → `letters/<session>/reminder-data.json` 생성.

   필요한 필드 (스크립트가 아직 없으면 이 모양으로 만든다):

   ```json
   {
     "session": "2026-08",
     "meetingDate": "2026-09-12",
     "meetingType": "online|offline",
     "meetingPlace": null,
     "voteClosed": false,
     "voteUrl": "https://monthly-checkin.vercel.app/vote",
     "commonQuestion": "이번 달 공통 질문 문장 (checkin_session_questions의 approved)",
     "writtenCount": 3,
     "totalMembers": 8,
     "members": [
       {
         "memberId": "",
         "name": "",
         "email": "",
         "wroteThisSession": false,
         "articleUrl": null,
         "lastWrittenSession": "2026-07",
         "missedStreak": 1,
         "recentSessions": ["2026-08:x", "2026-07:o", "2026-06:o"],
         "newReactions": [
           {
             "kind": "emoji",
             "emoji": "👍",
             "from": "",
             "targetType": "retrospective|comment",
             "articleUrl": ""
           },
           {
             "kind": "comment",
             "from": "",
             "body": "",
             "articleUrl": "",
             "commentId": ""
           }
         ],
         "lastArticleTitle": "",
         "lastArticleExcerpt": ""
       }
     ]
   }
   ```

   **데이터 소스 (실측 확인됨)**
   - `checkin_retrospectives` — `session`, `member_id`로 작성 이력·`missedStreak` 계산
   - `checkin_comments` — `retrospective_id`, `member_id`, `body`
   - `checkin_reactions` — `target_type`(`retrospective`|`comment`), `target_id`, `member_id`, **`emoji`**
   - `checkin_vote_polls` — `status`, `confirmed_date`, `confirmed_time`, `type`, `meeting_url`
   - `checkin_members` — 전체 로스터(현재 8명)
   - `checkin_session_questions` — 이번 달 공통 질문. `session`(회고 세션)당 하나, `approved`만 쓴다. 없으면 export가 경고하고 `commonQuestion`이 `null`이다 → 임의로 만들지 말고 관리자 화면에서 먼저 승인받는다

   반응은 좋아요(boolean)가 아니라 **이모지 반응**이다. 기본 이모지는 `src/types/index.ts`의 `DEFAULT_REACTION_EMOJIS`지만 임의 이모지도 들어온다.

4. **멤버 상태 분류** — 각 멤버를 아래 넷 중 하나로 판정한다. 분기별 본문 규칙은 §개인화 규칙 참고.
   - **A. 이미 썼음** (`wroteThisSession: true`)
   - **B. 아직 안 씀 · 최근 꾸준함** (`missedStreak === 0`)
   - **C. 아직 안 씀 · 두 달 이상 쉼** (`missedStreak >= 2`)
   - **D. 신규 / 첫 세션** (`recentSessions` 비어 있음)

5. **개인화 슬롯 채우기** — 멤버마다 아래를 만든다. 없으면 그 블록은 통째로 뺀다. 억지로 채우지 않는다.
   - `{name}` — 호칭
   - `{reactions}` — 지난 글에 새로 달린 이모지 반응·댓글. 댓글은 "누가 + 본문" + 딥링크 `{articleUrl}#comment-{commentId}`
   - `{callback}` — **이 메일의 핵심.** 지난달 회고에서 구체적인 대목 하나를 짚고 후속 질문을 붙인다 (§개인 콜백)
   - `{question}` — 이번 달 공통 질문 + "이거 한 줄만 써도 된다"는 안내
   - `{cta}` — `voteClosed: false`면 일정 투표 링크, `true`면 만남 정보(날짜·시간·장소 또는 웨일 링크)

6. **본문 작성** — 상태별 규칙(§개인화 규칙)에 따라 **4~7문장**. 다이제스트보다 짧게.
   데이터에 없는 근황·감상 지어내지 않는다. 갈피는 기록에 있는 것만 안다.

7. **템플릿 채우기** — `letters/_reminder-template.html`을 복사해 `letters/<session>/reminder-{nickname}.html`로 저장.
   비주얼 껍데기(색·폰트·보더·이미지 URL 구조)는 건드리지 않는다. 다이제스트 템플릿과 계열은 같되 마스트헤드 번호는 없다.

8. **자가 점검** — §체크리스트를 항목별로 확인.

9. **프리뷰 안내** — 생성된 파일 목록과 각 멤버의 분류(A~D), 한 줄 요약을 표로 출력하고, 브라우저로 열어 검토하라고 안내한다. 발송은 사용자가 직접, **한 통씩 개별 발송**.

10. **ledger 갱신 (발송 후)** — 사용자가 "발송했다"고 하면 `letters/galpi-reminders.json`의 `sent[]`에 `{ session, sentAt, memberIds }` 추가.

## 개인 콜백 — 이 메일의 핵심

전체 공지와 개별 메일을 가르는 건 이 한 문단이다. 없으면 이 메일을 보낼 이유가 없다.

**대상:** **직전 세션** 회고를 쓴 사람만. 지난달 회고가 없으면 **이 블록은 통째로 비운다.**
더 옛날 글을 억지로 끌어오지 않는다.

**구조 (3단):**

1. `지난 회고 잘 읽었습니다.` — 담백하게 연다
2. **구체적인 대목 하나** + `~라고 적어두셨더라고요.` — 본문에 실제로 있는 내용만. 요약 말고 그 사람만의 디테일로
3. **후속 질문** — 그 뒤로 어떻게 됐는지 묻는다

예시:

> 지난 회고 잘 읽었습니다. 사이드 프로젝트 「꼬붕단」이 출시 직전까지 왔다고,
> 앞으로가 더 문제일 것 같다는 말과 함께 적어두셨더라고요.
> 그 뒤로 출시는 하셨나요?

> 6월의 앨범으로 JMIN 「FOREVER KIDS」를 꼽으시고, 매 트랙마다 트랜지션이 들어가는데도
> 이지리스닝하기 좋다고 적어두셨더라고요.
> 7월엔 뭐가 그 자리를 차지했나요?

**고를 대목:** 미완결인 것(출시 직전, 다음 달에 쓰겠다고 한 것, 고민 중이라 적은 것)이 제일 좋다.
후속 질문이 자연스럽게 나오고, 답할 거리가 생긴다.

**금지:** 본문에 없는 내용 추가, 감상·평가("멋있으시네요"), 여러 대목 나열. **한 대목 + 한 질문.**

## 개인화 규칙

**A. 이미 썼음**
고맙다는 인사 → 받은 반응 안내(`{reactions}`) → 마무리. 재촉할 게 없으니 짧게 끝낸다. 3~4문장.
반응이 하나도 없으면 반응 얘기를 꺼내지 않는다. "아직 아무도 안 봤어요"는 최악이다.

**B. 아직 안 씀 · 최근 꾸준함**
안부 → 이번 세션이 열려 있다는 사실만 알림 → `{question}` → 한 줄도 괜찮다는 안내.
이 사람은 원래 쓰던 사람이라 알림만으로 충분하다. 설득하려 들지 않는다.

**C. 아직 안 씀 · 두 달 이상 쉼**
**가장 조심할 분기.** 쉰 기간을 세지 않는다("두 달째 안 쓰셨네요" 금지). 사과를 유도하지 않는다.
대신 `{lastEcho}`로 마지막 글을 조용히 꺼내고, 자리가 그대로 있다는 사실만 전한다.
갈피라는 이름이 "돌아올 자리를 표시해두는 것"이니 이 분기가 캐릭터의 존재 이유다. `{question}` 붙이고 끝.

**D. 신규 / 첫 세션**
모임이 어떻게 굴러가는지 3줄 안내 + `{question}` + CTA. 개인화할 데이터가 없으니 억지로 친한 척하지 않는다.

## 톤 규칙

- **검사하지 않는다.** "지난 액션 지켰어요?" 계열 문장은 이 프로젝트의 출발점이 된 반면교사다.
- **비교하지 않는다.** `writtenCount`는 "벌써 세 분이 썼어요" 정도의 사실 전달까지만. 누가 썼는지 이름은 넣지 않는다.
- **분량으로 압박하지 않는다.** 항상 "한 줄이어도 된다"가 깔려 있어야 한다.
- **사서 메타포를 쓰지 않는다** — 가이드 §8의 공통 규칙. 리마인더는 특히 조심할 것:
  "자리를 비워뒀다" 계열이 **"당신이 없었다"를 전제**해서, 안 쓴 사람에게 은근한 압박이 된다.
- **담백하게.** 꾸미는 말보다 사실과 질문. 이모지는 없어도 된다.
- **남은 날짜를 세지 않는다.** "일주일 남았어요 / 이제 3일이에요 / 내일이에요" 같은 카운트다운 금지.
  발송 시점이 매번 달라서 틀리기 쉽고, 무엇보다 재촉으로 읽힌다. 모임 날짜는 CTA 블록에 **사실로만** 적는다.
- 갈피는 **사서**다. 독촉하는 간사가 아니라 자리를 지키고 있는 쪽이다.
- 이모지는 서명 근처 최대 1개. 느낌표 남발 금지.

## 발송 전 체크리스트

- [ ] 멤버 수만큼 파일이 생성됐는가
- [ ] **다른 사람 이름·내용이 섞여 들어가지 않았는가** (개별 메일 최대 사고)
- [ ] 이미 쓴 사람에게 "쓰세요" 문구가 남아 있지 않은가
- [ ] C 분기에 쉰 기간·횟수를 세는 표현이 없는가
- [ ] 본문에 남은 날짜 카운트다운("N일 남았어요")이 없는가
- [ ] 데이터에 없는 내용을 지어내지 않았는가
- [ ] 콜백에서 짚은 대목이 **지난달 회고 본문에 실제로 있는가** (문자열로 대조)
- [ ] 지난달 회고가 없는 사람에게 콜백이 들어가지 않았는가
- [ ] 사서 메타포(서가·자리·보관·꺼내읽다)가 남아 있지 않은가
- [ ] 댓글 딥링크가 해당 댓글로 가는가

## 하지 않을 것

- Gmail `create_draft` 사용 금지 (HTML 렌더 깨짐 — 사용자가 직접 발송).
- **여러 명을 한 통에 묶지 않는다.** 참조·숨은참조 발송 금지. 개별 메일의 전제가 무너진다.
- 다른 멤버가 쓴 글의 내용을 이 메일에 요약해 넣지 않는다. 그건 다이제스트의 일이다.
- 템플릿 색·타이포·레이아웃 임의 변경 금지 (가이드에 없는 비주얼 변경은 사용자 확인).
- 상태 분류가 애매하면 임의로 정하지 말고 사용자에게 묻는다.
